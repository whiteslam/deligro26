Critical

C1Customers can set their own item prices on prod until 0053 is applied

Where 0001_init.sql:258-262 (order_items insert policy checks only ownership); the fix is 0053_release_hardening.sql:98-146, which is unapplied.

Impact Using the public publishable key, someone can insert order_items directly with price: 1, or add items to an accepted order, then call recompute_order_total. The rider collects ₹1 and the vendor is settled on ₹1. Before 0053, orders can also be inserted with a forged status, channel or placed_by.

Fix Apply 0053 (after C2), then run the runbook verify queries.

C2Applying 0051 as written breaks every checkout

Where 0051_cancellation_provenance.sql:~191-226 redeclares guard_order_update as security definer without the current_user exemption. 0053's own header confirms this.

Impact It brings back the 2026-08-13 incident: recompute_order_total is refused and checkout returns 500. The file says "safe to re-run", so re-running it after 0053 breaks prod again.

Fix Before applying, edit 0051 in place so its guard body is the 0053 version. That is safe because 0051 has never run on prod.

High

H1The telemetry partition obs_events_default is open to anon

Where Created at 0046_observability.sql:139, but it is missing from the RLS/revoke loop at :498-514.

Impact Anyone holding the publishable key can insert unlimited rows (filling the DB) and read telemetry: stacks and order/driver UUIDs.

Fix alter table public.obs_events_default enable row level security; revoke all on public.obs_events_default from anon, authenticated;

H2Riders and vendors can read the delivery OTP and set any order status directly

Where The orders read and update policies (0001:232-253) have no column grants; delivery_otp comes from 0006:51; there is no transition check in the DB. The comment in handover.ts:15 ("only the order owner can read") is wrong.

Impact Using their own JWT, a rider can read the code and complete a delivery without the customer, or PATCH status='delivered'. A vendor can mark its own orders delivered, and those count in settlements.

Fix Grant orders SELECT through a column allowlist that leaves out the OTPs, and serve the customer's code through a definer RPC. Add both OTPs to the locked list. Add a status-transition trigger.

H3Admin data functions trust the layout's role check

Where 44 src/app/admin/**/page.tsx files have no guard of their own. Service-role helpers rely on the layout: admin-vendors.ts:587 says "The caller is already requireRole("admin")-gated". listVendors attaches plaintext vendor passwords.

Impact Next.js does not re-run a layout on every navigation request, and its docs warn against layout-only auth. Exploitability is unverified and needs testing on staging. If it is exploitable, a customer account could read every vendor password and customer PII.

Fix Put await requireRole("admin") at the top of every exported function in the admin-*.ts, vendor-credentials.ts, cod-handovers.ts, operational-expenses.ts and employees.ts modules. lib/obs/read.ts already does this.

H4The OTP attempt counter can be raced, and there is no per-phone verify limit

Where src/lib/data-access/otp.ts:117-135 does read → compare → write attempts + 1. api/auth/otp/verify is limited per IP only (20/h).

Impact Parallel guesses get past the 5-try lock. OTP signs in to any role, and the admin phone is committed in src/lib/developers.ts:11.

Fix Increment atomically (update … where attempts < 5 returning) before comparing, and add a per-phone verify limit. Do the same in checkOtp.

H5Anon can lock any staff member out of password login (until 0053)

Where 0027_rate_limits.sql:112 revokes from PUBLIC only; the keys are predictable (pw-login-phone:+91…). The fix is in 0053:217.

H6Push identity can be hijacked

Where mobile/native/DeligroPushPlugin.java:31-38 calls OneSignal.login(userId) with no identity verification; the server targets external_id (onesignal.ts:185).

Impact Anyone who knows a profile UUID can receive that user's pushes.

Fix Turn on OneSignal Identity Verification (a server-signed JWT).

H7Installed APKs never check for updates, though the docs say they do

Where Nothing in src/ calls /api/app-version; the user agent carries no versionCode (mobile/scripts/lib.mjs:49); the route only knows rider and customer.

Impact A broken sideloaded build can never be pushed out or forced to update.

H8Home-screen search never finds a dish (regression)

Where (customer)/page.tsx:19 loads withMenu:false, but home-view.tsx:84 still indexes dishes from those menus, which are now empty.

Impact Typing "paneer" on Home shows "No kitchen near you is cooking that", which is false.

Fix Short term: send the Home search to /search?q=.

H9The Observatory has almost no data to show

0 of 38 route.ts files use withObservability, so there is no request timing and no 4xx/5xx visibility. pg_cron jobs exist only as commented-out SQL (0046:1109-1112), so rollups, alerts and retention never run. All 8 alert rules ship disabled, and alerts reach nobody. Render crashes outside /admin are only console.error'd (app/error.tsx, global-error.tsx, manager/error.tsx). Razorpay calls, dispatch and OTP verify emit no events, so their alert rules can never fire.

Medium

M1Fee and tax can be forged on a direct order insert: still open after 0053 (residual noted in 0030:184-194). Derive both in recompute_order_total.
M2Riders can rewrite their whole deliveries row, including cod_collected_amount (0001:272-274). Restrict UPDATE to the location columns.
M3Column grants that do nothing: reviews/review_replies (a customer can move a review to another shop), payments and category_images. Table-level privileges were never revoked first.
M4Vendors can edit rating*, promoted, sort_position and payout fields, which the 0034 lock does not cover.
M5Customers can set their own wallet_balance (unused today; lock it before anything reads it).
M6The rider can brute-force the delivery OTP: a 4-digit code with 10 tries a minute and no per-order counter (driver/actions.ts:49).
M7Write endpoints without a rate limit: 3 upload routes, menu availability, avatar delete, and almost every admin, vendor and manager server action. This breaks AGENTS.md rule 6.
M8/api/obs/client has no body-size cap, and random messages create unlimited new issues. /api/banners/track doesn't validate bannerId or placement.
M9The app stays degraded after a migration until restart: schema-probe.ts and flags.server.ts latch "missing" for the life of the process. Add "redeploy" to the runbook.
M10Missing hot indexes on orders(restaurant_id,status,created_at), orders(customer_id,created_at) and deliveries(status,offered_at). RLS helpers are called per row; wrap them as (select is_admin()).
M11Vendor analytics bucket by server time, not IST (vendor-earnings.ts:328,345; vendor-overview.ts:178), so the hourly chart is shifted 5.5 h on a UTC host.
M12Service-worker caches grow forever (SW_VERSION="v1", no entry cap). Polling every 4 s on rider phones even when the app is hidden. Vendor recharts is loaded eagerly. /search ships every menu.
M13Hindi-first audience, but DEFAULT_LANG="en" and <html lang="en"> is hard-coded. The kitchen and rider boards are mostly English.
M14APK build is not reproducible (unpinned Capacitor/OneSignal). Every role requests location permission, and riders have no background location. allowBackup is not disabled. Razorpay 3DS inside the WebView is untested.
M15No migration ledger: duplicate prefixes 0008, 0009, 0015 and 0033, and gaps at 0004 and 0038. What is applied on prod is only known from memory.

  • The README is stale (English-only, COD-only, demo mode). There are two lockfiles. 11 reports sit at the repo root and could move to docs/reports/.
