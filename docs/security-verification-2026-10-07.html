Deligro security verification

Live Supabase project and codebase · 7 October 2026 · read-only checks

Bottom line

No way for a logged-out visitor to read private data was found. Row-level security is on for every table, order totals and payment status are locked by database triggers, and private tables return nothing to anonymous requests. Three small leftover permissions were found. They were fixed by migration 0054, and blocks 3 and 4 were re-run afterwards to confirm. Nothing needs to stop the handover.

About the address in the HTML

A separate review of the home page HTML flagged Home · B.t.i.colony as a possible leak of a customer's location. It is not. The home page reads the logged-in user's own saved address through row-level security, on a page built per request. The address shown is the viewer's own. The only related risk is finding 4, the on-device cache. The other claims in that review (chunk paths, company name, theme setting) are normal for a Next.js app.

What was not checked

  • Anonymous writes were not tested against the live database. Anonymous users hold write privileges on most tables (Supabase's default), so the protection is row-level security alone. It is on everywhere, but it was not exercised with a real write attempt.
  • Cross-account access for logged-in users (one customer reading another's order) was not tested live. The suite for that is npm run test:idor. It creates QA accounts on the live database, so it needs your explicit go-ahead.
  • The live Cache-Control header on the home page was not confirmed.
  • The Google Maps key restriction (by domain or app) can only be checked in Google Cloud.
  • Application code was read for the areas above, not fully audited.
