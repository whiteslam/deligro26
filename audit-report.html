HIGH Nothing in the app is actually realtime — every 'live' surface is a polling loop realtime
src/components/shared/auto-refresh.tsx:28 · src/hooks/use-live-tracking.ts:171 · supabase/migrations/ (all 40)

The word 'live' appears throughout the product, but there is not a single Supabase Realtime channel in the codebase. `AutoRefresh` calls `router.refresh()` on a timer — 4s on the admin orders board, manager board and driver board, 8s on the vendor kitchen board — which re-executes the ENTIRE server component tree and every database query behind it, then streams a fresh RSC payload down. The customer tracking screen polls `/api/orders/:id/tracking` every 3s. Three consequences. (1) Cost and load: one vendor tablet left open for a 10-hour service day fires ~4,500 full board re-renders, each running the vendor-orders query set. Ten vendors, two admins and four drivers online is roughly 100,000 needless database round trips a day, and Supabase bills egress. (2) Latency the kitchen feels: a new order takes up to 8 seconds to appear on the vendor board, and the customer waits up to 3s plus a full round trip to see 'accepted'. (3) It scales the wrong way — the load is proportional to open tabs, not to orders. No migration adds any table to the `supabase_realtime` publication, so the feature is off at the database as well as absent in the client.

Fix

The groundwork is already done — `next.config.ts:31` already allows `wss://*.supabase.co` in connect-src, so no CSP change is needed.

1. Enable replication on the two tables that matter:

```sql
-- supabase/migrations/0038_realtime.sql
alter publication supabase_realtime add table public.orders;
alter publication supabase_realtime add table public.deliveries;
alter table public.orders replica identity full;
alter table public.deliveries replica identity full;
```
RLS applies to Realtime, so each role only receives the rows it may already read.

2. Replace the timer in `AutoRefresh` with a change-triggered refresh, keeping a slow poll as a safety net:

```tsx
useEffect(() => {
  const supabase = createBrowserClient();
  const ch = supabase
    .channel(`orders-board`)
    .on('postgres_changes',
        { event: '*', schema: 'public', table: 'orders' },
        () => router.refresh())
    .subscribe();
  // Net, not the mechanism: catches a dropped socket.
  const id = setInterval(() => { if (!document.hidden) router.refresh(); }, 60_000);
  return () => { supabase.removeChannel(ch); clearInterval(id); };
}, [router]);
```

This cuts the vendor board from ~4,500 refreshes a day to roughly one per order plus 600 heartbeats, while making the kitchen alert fire in well under a second instead of up to eight.
You must do this yourself: Enable Realtime for the `orders` and `deliveries` tables in the Supabase dashboard (Database → Replication) after running the migration.
HIGH English-only interface for a Hindi-speaking tier-3 city ux
src/app/layout.tsx:52 (`lang="en"`) · no i18n library, no locale files, no translated strings anywhere in src/

Every string in the product — 'Craving to doorstep', 'Track order', 'Reorder', 'Cash on delivery', 'Your order is on the way' — is English only. Bemetara is a Hindi-speaking district in Chhattisgarh. A meaningful share of the target customers, and very likely most of the delivery riders and several of the restaurant staff who have to operate the vendor board, read Devanagari far more comfortably than Latin script. This is the single largest barrier to the app being 'very easy to understand' for the stated audience, and no amount of layout polish compensates for it. It also affects the operator surfaces: a rider who misreads 'Mark delivered' vs 'Mark picked up' creates a real support incident.

Fix

Hindi is a UI-string problem, not a full i18n-framework problem, because there is one city and one currency. Ship a lightweight dictionary rather than pulling in next-intl:

```ts
// src/lib/i18n/strings.ts
export const STRINGS = {
  en: { trackOrder: 'Track order', onTheWay: 'On the way', cod: 'Cash on delivery' },
  hi: { trackOrder: 'ऑर्डर ट्रैक करें', onTheWay: 'रास्ते में', cod: 'डिलीवरी पर नकद' },
} as const;
```

Order of work, highest value first:
1. **Customer order-status words** — the six tracking stages and the cart/checkout buttons. This is ~40 strings and covers the moments that generate support calls.
2. **Driver board** — ~15 strings. Riders are the least likely group to read English.
3. **Vendor board** — ~30 strings.
4. Admin console can stay English; it is used by you.

Add a language toggle in Profile, persist it the same way `deligro-theme` already is in `src/app/layout.tsx:40`, and set `<html lang>` from it. Consider defaulting to Hindi with an English toggle rather than the reverse — the default should match the majority user.
You must do this yourself: Get the Hindi strings reviewed by a native Chhattisgarhi Hindi speaker, not machine translation. Delivery vocabulary is regional and a stilted translation reads worse than English.
HIGH The entire customer app is login-walled and invisible to Google SEO
src/proxy.ts:91 · no src/app/robots.ts · no src/app/sitemap.ts · src/app/(customer)/restaurant/[slug]/page.tsx (no generateMetadata)

`src/proxy.ts:91` redirects any visitor without a session or guest cookie to `/login`. Googlebot has neither, so every crawl of every URL returns a redirect to a sign-in page. The result is that the site has effectively zero indexable surface. There is no robots.txt, no sitemap.xml, no canonical tag, no Open Graph image, and no JSON-LD. Restaurant pages — the only genuinely valuable SEO asset a delivery business owns — carry no metadata at all and inherit the root title 'Deligro — Craving to doorstep', so all of them are duplicates to a crawler. For a single-city operator this is the difference between owning the 'food delivery bemetara' and 'best biryani bemetara' queries and being invisible on them. It also breaks link sharing: a restaurant link pasted into WhatsApp — the dominant sharing channel for this audience — renders with no image, no name and no description.

Fix

Let crawlers and cold visitors read the menu; keep the login wall only where it protects data.

1. In `src/proxy.ts`, allow browse routes through without a session:
```ts
const PUBLIC_BROWSE = ['/', '/search', '/restaurant', '/stores'];
// …after the PUBLIC_PATHS check, before the guest gate:
if (matches(path, PUBLIC_BROWSE)) return response;
```
`/checkout`, `/orders` and `/profile` stay gated by the existing `GATED_CUSTOMER` list, so nothing that touches user data opens up.

2. Add per-restaurant metadata and structured data:
```tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const { slug } = await params;
  const r = await getRestaurantBySlug(slug);
  if (!r) return {};
  return {
    title: `${r.name} — order online in Bemetara | Deligro`,
    description: `Order ${r.cuisines.join(', ')} from ${r.name}. Delivered in about ${r.etaMin} minutes.`,
    alternates: { canonical: `/restaurant/${slug}` },
    openGraph: { title: r.name, images: [r.imageUrl], type: 'website' },
  };
}
```
Add `Restaurant` JSON-LD with `servesCuisine`, `aggregateRating` and `areaServed: 'Bemetara'`.

3. Add `src/app/robots.ts`, `src/app/sitemap.ts` (enumerating approved restaurants), and `metadataBase` in the root layout.
You must do this yourself: Register the domain in Google Search Console and submit the sitemap once deployed. Also create a Google Business Profile for the city — for tier-3 local search that often outperforms organic.
MEDIUM 15px base type with pinch-zoom disabled — the two problems compound ux
src/app/layout.tsx:32 (`maximumScale: 1`) · src/app/globals.css:519 · 416 occurrences of `text-xs` or smaller across src/

The base font is set to 15px with the comment 'Slightly denser than browser default 16px', and the codebase uses `text-xs` (12px) or smaller in 416 places, with a documented 11px caption size and several 11.5px operator-console sizes. Separately, `maximumScale: 1` in the viewport disables pinch-zoom. Either alone is a minor issue; together they are not, because zoom is precisely the escape hatch a user with weak near vision reaches for when text is too small, and it has been removed. This fails WCAG 1.4.4 (Resize Text). The audience skews toward first-time smartphone users, older shopkeepers operating the vendor board, and riders reading a phone in daylight on a bike — all of whom need larger targets and text, not denser.

Fix

Two small changes, immediate effect:

```diff
// src/app/layout.tsx
 export const viewport: Viewport = {
   width: 'device-width',
   initialScale: 1,
-  maximumScale: 1,
 };
```

```diff
/* src/app/globals.css */
-  font-size: 15px; /* Slightly denser than browser default 16px */
+  font-size: 16px;
```

Then raise the floor on the customer-facing surfaces: no body or label text below 14px, and 16px for anything the customer must read to make a decision (prices, dish names, order status, the total). Note that inputs below 16px also cause iOS Safari to auto-zoom on focus, which is a real annoyance in the checkout form.

Audit tap targets to a 44×44px minimum while you are in there — the quantity steppers and the category chips are the likely offenders.

public/ (no manifest.json) · no src/app/manifest.ts · public/OneSignalSDKWorker.js exists but no app service worker

```ts
    theme_color: '#0f1215',
    icons: [
      { src: '/icons/icon-192.png', sizes: '192x192', type: 'image/png' },
      { src: '/icons/icon-512.png', sizes: '512x512', type: 'image/png' },
      { src: '/icons/icon-512-maskable.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' },

```
The brand marks already exist at `Resources/deligro-icon.svg` and `Resources/deligro-mark.svg` — export them to PNG at both sizes. Include a maskable variant or Android will letterbox the icon in a white circle.
MEDIUM No offline or weak-network handling outside the tracking screen functionality
src/components/orders/tracking-view.tsx:259 (the only offline affordance in the app)

The live tracking screen has a genuinely well-built staleness indicator — `use-live-tracking.ts` counts failed polls, freezes the rider pin rather than animating a courier that may not be moving, and shows a WifiOff banner. That care is not applied anywhere else. Nothing else in the app reads `navigator.onLine`. On a dropped connection the home feed, search, restaurant menu and — most damagingly — the checkout Place Order button all fail silently or hang. In a tier-3 city on patchy 4G this is a routine condition, not an edge case, and the worst outcome is a customer tapping Place Order three times on a stalled request because nothing told them the network was gone.

Fix

Two pieces.

1. A global connection banner, mounted in the customer layout:
```tsx
'use client';
export function OfflineBanner() {
  const [online, setOnline] = useState(true);
  useEffect(() => {
    const on = () => setOnline(true), off = () => setOnline(false);
    setOnline(navigator.onLine);
    window.addEventListener('online', on);
    window.addEventListener('offline', off);
    return () => { window.removeEventListener('online', on); window.removeEventListener('offline', off); };
  }, []);
  if (online) return null;
  return <div role="status" className="…">No internet — showing what we last loaded</div>;
}
```

2. Make the checkout submit explicitly network-aware: disable the button while a request is in flight (guarding against double-submit), give the fetch a timeout, and on failure show 'Could not reach Deligro — check your connection and try again' with a retry, rather than leaving a dead button.

A service worker caching the shell and the restaurant list would go further, and pairs naturally with the manifest above.
MEDIUM router.refresh() polling re-runs entire server trees, including heavy admin queries Performance
src/app/admin/orders/page.tsx:216 (4s) · src/app/manager/page.tsx:56 (4s) · src/components/driver/driver-board.tsx:291 (4s) · src/components/vendor/vendor-orders-board.tsx:843 (8s, `whenHidden`)

Beyond the realtime finding above, the vendor board polls with `whenHidden` set — deliberately, and the reasoning in the code is sound (a kitchen tablet asleep on another tab must not miss orders). But the consequence is that a forgotten open tab polls forever, at full server-render cost, with nobody watching. The admin orders page re-runs `listAllOrders` over a 50-row window plus `listPendingRestaurants` every 4 seconds. `src/lib/data-access/admin-settlements.ts` is 1,829 lines of query logic; anything on that path being polled is expensive. This is also the main reason the performance axis scores as it does — the code itself is efficient, but it is executed far more often than the data changes.

Fix

Fixing the realtime finding fixes most of this. Until then, two cheap mitigations:

1. Back off when nothing is happening. If three consecutive refreshes return identical data, stretch the interval to 30s; reset on any change. A kitchen with no orders should not cost the same as a kitchen at dinner rush.
2. Cap the `whenHidden` poll: after 60 minutes with no visibility event and no new order, stop and show a 'Reconnect' button on return. A tablet in a drawer should not poll overnight.

MEDIUM Four pairs of migrations share a version number Code Quality
supabase/migrations/ — 0008, 0009, 0015 (`0015_orders_external_id.sql` + `0015_platform_settings.sql`), 0033 (`0033_drop_mfa.sql` + `0033_reviews.sql`)

Migration order is defined by filename, and four numbers are used twice. Within a pair the apply order is decided by lexical sort of the description — `0033_drop_mfa` runs before `0033_reviews` because 'd' precedes 'r', which is arbitrary rather than intended. Today the pairs happen not to depend on each other, so nothing is broken. The risk is forward-looking: the next duplicate may pair a table creation with something that references it, and it will fail on a fresh database while continuing to work on the existing one — the worst failure shape, because it only appears when you rebuild staging or onboard a new environment.

Fix

Do not renumber applied migrations — that breaks the migration ledger on the live database. Instead:

1. Record the intended order in `supabase/migrations/README.md`, noting that the four duplicate pairs are order-independent and verified as such.
2. Adopt timestamp-prefixed names for everything new (`20260819120000_realtime.sql`), which the Supabase CLI generates by default and which cannot collide.
3. Add a pre-commit or CI check that fails on a duplicate numeric prefix.
4. Verify by applying all migrations to an empty database — if `supabase db reset` succeeds cleanly, the current order is genuinely safe.
You must do this yourself: Run `supabase db reset` against a scratch project to confirm the full chain applies from empty. This is the only way to prove the duplicates are harmless.
MEDIUM About 50 files import `server-only`, which is not declared as a dependency Code Quality
src/lib/auth.ts:1 and ~49 other files under src/lib/ · package.json (no `server-only` entry)

`server-only` is the guard that makes a build fail loudly if a server module is ever pulled into a client bundle — it is the mechanism protecting the service-role Supabase client and every data-access module from leaking into the browser. It works today only because it resolves transitively through Next.js. Under pnpm's strict node_modules layout that is not guaranteed: a Next version bump that stops re-exporting it, or a switch to a stricter hoisting setting, makes ~50 imports fail to resolve. The failure is loud rather than silent, so this is a build-stability issue rather than a security hole — but it is a load-bearing security mechanism resting on an undeclared dependency, which is worth one line of package.json to fix.

Fix

```diff
// package.json
   "dependencies": {
+    "server-only": "^0.0.1",
     "@supabase/ssr": "^0.12.0",
```
Then `pnpm install`. No source changes.
LOW CSP allows 'unsafe-inline' for scripts, and the upgrade path is already documented Security
next.config.ts:22

`script-src` includes `'unsafe-inline'`, which removes most of the XSS protection a CSP provides — if an injection point is ever introduced, the policy will not stop the payload. The comment at `next.config.ts:14` is honest about this being the 'pragmatic budget tier' and names the fix. The practical risk today is low: React escapes by default, there is exactly one `dangerouslySetInnerHTML`-shaped construct (the theme bootstrap in `src/app/layout.tsx`), and no user-controlled HTML is rendered anywhere. Recording it because it is the one place where a documented control is weaker than it reads.

Fix

Generate a per-request nonce in `src/proxy.ts`, pass it to the one inline script (`InlineScript` already wraps it, so there is a single call site), and drop `'unsafe-inline'`:

```ts
const nonce = crypto.randomUUID();
response.headers.set('x-nonce', nonce);
// script-src 'self' 'nonce-${nonce}' https://cdn.onesignal.com …
```

Worth doing before you handle card payments at volume; not urgent at current scale.

What's new &mdash; modernization

  • Next.js 16.3 and React 19.2 are current — no framework upgrade needed, and AGENTS.md correctly warns that this Next version's conventions differ from older training data.
  • Supabase Realtime is available on the existing plan and already permitted by the CSP; the app predates its own need for it and never adopted it.
  • Next 16's `proxy.ts` convention is correctly adopted (formerly middleware.ts) — good sign the codebase is being kept current.
  • No error monitoring. Sentry or a Supabase-logged error boundary would surface the failures the code carefully handles but never reports.
  • No automated tests in CI. scripts/qa/ contains a real suite (idor-suite, payments-signature, e2e-smoke, zap-baseline) that appears to be run by hand — wiring it to GitHub Actions is the single highest-leverage DX change available.

Suggestions

  • Order-status SMS as a fallback to web push. Push only reaches an installed or permission-granted browser; Renflair is already integrated for OTP, so a single 'Your order is on the way' SMS costs one API call and reaches every phone regardless of browser state.
  • A repeat-order shortcut on the home screen. In a single-city market the same customers order from the same three shops — surfacing 'Order again' as the first block beats any amount of discovery UI, and reorder logic already exists.
  • Show the delivery OTP larger on the tracking screen. getDeliveryOtp is already fetched; a rider and customer reading a 4-digit code to each other at the door need it at display size, not caption size.
  • Add a WhatsApp share button on restaurant pages. It is the dominant sharing channel for this audience, and fixing the OG tags (see the SEO finding) is what makes the shared link render properly.
  • Consider whether guest browsing should be the default rather than an opt-in below the OTP form. Requiring a phone number before a first-time user can see a single dish is a hard bounce for the least confident users.
  • Icons alongside text on the driver and vendor boards. Riders scanning a phone one-handed benefit from a shape they recognise before they read the word — and this partly hedges the language gap while translation is in progress.
  • Wire scripts/qa/run-all.sh into CI on every push to main. The suite exists and is good; running it by hand means it eventually stops being run.
