Overall health

Running the app found that the SEO and PWA work from the first fix pass was completely inert: robots.txt, sitemap.xml and manifest.webmanifest all answered 307 redirect to /login for anonymous requests, because src/proxy.ts's matcher did not exclude them. Googlebot has no session, so the sitemap listing 50 restaurants was unreachable, and so was the manifest that makes the app installable. HIGH FIXED — robots.txt, sitemap.xml and manifest.webmanifest all answered 307 to /login SEO
src/proxy.ts:101 (matcher) · src/proxy.ts:91 (session gate)

All three files were generated correctly by src/app/{robots,sitemap,manifest}.ts and appeared in the build output — the exact thing verified during the previous fix pass, and not sufficient. The proxy matcher excluded _next/static, _next/image, favicon.ico and image extensions but not these three, so every anonymous request fell through to the session gate and was redirected. Googlebot has no session. The consequences were all silent: a crawler cannot read robots.txt so it never discovers the sitemap; it cannot read the sitemap so no restaurant page is indexed; a first-time visitor's browser cannot read the manifest so Chrome never offers 'Add to home screen' — precisely the visitor the manifest exists for. The entire SEO and PWA fix was inert from the moment it shipped.

Fix

One line, in the matcher:

```diff
-"/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)"
+"/((?!_next/static|_next/image|favicon.ico|robots\\.txt|sitemap\\.xml|manifest\\.webmanifest|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)$).*)"
```

All three are public by definition — nothing in them is user-scoped, so there is nothing for the session gate to protect. Verified on a running production server: robots.txt 200, sitemap.xml 200, manifest.webmanifest 200, while /admin and /checkout still answer 307. The lesson worth keeping: 'it appears in the build output' is not 'it is reachable' — every public file needs one HTTP request against a running server before it counts as shipped.
HIGH Every catalog page ships the entire city's menu — 3,157 dishes Performance
src/lib/search/dishes.ts:9 · src/lib/catalog.ts:33 · src/app/(customer)/page.tsx:13

Measured on a production build: / is 1,210,678 bytes raw (81KB gzipped, 1.3-2.5s server render), /search 1,248,670 bytes, /stores 1,200,779 bytes — while /restaurant/[slug], the page that shows one real menu, is 38,788 bytes (10KB gzipped, 0.5s). The page showing no menu is 30x larger than the page showing one. Payload composition of the home page: 3,207 price fields, 3,157 veg flags, 3,167 descriptions — the full menu of all 50 approved restaurants, confirmed against the database (50 approved restaurants, 3,797 menu items). This is deliberate and documented: dishes.ts says the catalog is loaded whole so client-side search 'stays instant while typing'. It is the wrong trade for this audience. Instant local search is a luxury; 81KB of gzipped HTML plus 1.2MB to parse and hydrate on a low-end Android over patchy 4G is a cost paid on every visit by everyone, including the majority who never search. It also grows linearly with onboarding — at 100 vendors it doubles.

Fix

Move search server-side at the seam the code already names (`buildDishIndex`).

1. A feed projection without menus:
```ts
// name, image, rating, eta, cuisines, price tier — no menu array
export async function listRestaurantsForFeed(): Promise<RestaurantCard[]>
```
2. A search endpoint, debounced ~250ms client-side:
```ts
// GET /api/search?q=... over menu_items
```
3. The index that makes it fast:
```sql
create extension if not exists pg_trgm;
create index on menu_items using gin (name gin_trgm_ops);
```

Expected: the home page drops from ~81KB to well under 15KB gzipped and stops growing with the vendor count; search costs one debounced request instead of a megabyte up front.
MEDIUM No <h1> on the home, search or stores pages SEO
src/app/(customer)/page.tsx · src/app/(customer)/search/page.tsx · src/app/(customer)/stores/page.tsx

Measured on rendered HTML: / has 0 h1, 3 h2 and 56 h3. /search and /stores also have 0. Only /restaurant/[slug] has one. Screen-reader users navigate by heading level and a crawler reads the h1 as the page's subject, so this is a single defect scoring against both accessibility and SEO on three of the four main customer pages. The 56 h3 card titles with no h1 or h2 above them is not a hierarchy, it is a flat list wearing heading tags.

Fix

Give each page one <h1> — styled as the design already looks, or `sr-only` where there is no room for a visible title — and demote the card titles from h3 so the levels descend properly. On the home page the h1 is the greeting or 'Order in Bemetara'; on /search it is 'Search'; on /stores, 'All restaurants'.
MEDIUM Admin cannot assign a rider, although the server action already authorizes admins functionality
src/app/manager/actions.ts:105 (assignRider) · src/components/admin/live-board.tsx (renders "Unassigned", no action)

`assignRider` is a well-built action — role-checked as ["manager", "admin"], handles the duplicate-key race with a human message ("A rider took this order first"), and degrades gracefully on a database without migration 0026's location-source column. It is called from exactly one component: the manager order board. The admin console's LiveBoard renders the word "Unassigned" in its rider column with nothing to click. So an admin watching a stuck order can see the problem and cannot fix it, despite the server already permitting them to. The only other path to a delivery row is a driver self-claiming through acceptDelivery, so if no rider is online an order sits in READY with no escalation and no operator able to intervene from the console they are already in.

Fix

Surface the existing action in the LiveBoard's rider cell — a small picker on the "Unassigned" label, calling the same `assignRider(orderId, riderId)`. No permissions change is needed; the authorization already covers admin. This is purely a UI gap.

Suggestions

  • Add a CI smoke check that fetches /robots.txt, /sitemap.xml and /manifest.webmanifest against a started production server and fails on anything other than 200. This exact class of bug — correct file, unreachable route — is invisible to typecheck, lint and build, all three of which passed.
  • Order-status SMS as a fallback to web push; Renflair is already integrated for OTP and reaches every phone regardless of browser state.
  • Show the delivery OTP at display size on the tracking screen — it is already fetched, and two people reading a 4-digit code at a door need it large.
  • Icons alongside text on the driver and vendor boards; a rider recognises a shape before reading a word, which also partly hedges the language gap while translation is in progress.
  • Test on a real low-end Android over a throttled connection. Given the catalog payload finding, INP on the home page is where I would look first.
