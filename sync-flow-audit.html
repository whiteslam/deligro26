Sync & Flow Audit — Customer · Vendor · Rider · Admin

How an order's state travels between the four apps, how long each hop takes, and where it silently doesn't arrive. Read from the code on 28 Sept 2026. Nothing was changed and no live data was touched.

0Supabase Realtime channels. All sync is polling
3–8 sWorst-case delay between apps while the screen is on
UnboundedDelay for vendors and riders when their screen is off
1 of 4Roles that can get a push notification (customer only)
The bottom line. While every app is open and on screen, the platform stays in sync within about 2–8 seconds, which is fine for food delivery. The problem is the moment a phone goes in a pocket. Vendors and riders never register for push notifications: OneSignalInit is mounted only in the customer layout. The rider board also stops polling when hidden. So a new order or a rider offer is only found when someone looks at the screen. That gap, not the poll speed, is what costs you minutes.

1 · How sync works today

There are three channels. None of them is a live connection.

  1. Page polling (router.refresh()): AutoRefresh (src/components/shared/auto-refresh.tsx) re-renders the whole server page on a timer. It pauses when the tab is hidden, except on the vendor board (whenHidden). It also refreshes immediately when the tab regains focus.
  2. API polling: the customer tracking screen calls /api/orders/:id/tracking every 3 s (src/hooks/use-live-tracking.ts:181), only while visible, and stops once the order is delivered or cancelled.
  3. Push (OneSignal): src/lib/notifications/order-events.ts sends a push on each transition. In practice only customers ever have a push id saved.

4 · Findings

P0 Vendors and riders never register for push

<OneSignalInit /> is rendered only in src/app/(customer)/layout.tsx:60. The vendor, driver, manager and admin layouts never load the SDK, so profiles.onesignal_id stays empty for them. notifyVendorNewOrder, notifyVendorOrderCancelled, notifyDriverPickupOffered and notifyDriverPickupReady all return early with nobody to send to. The exception is a vendor or rider who once used the customer app on the same login. The rider APK may register natively; that code isn't in this repo, so check it.

The OneSignal keys are set in .env.local now, so the comment in kitchen-alert.tsx:17-23 ("credentials are unset") is stale.

P0 Rider board stops polling when hidden, which also disables its alert

driver-board.tsx:512 uses <AutoRefresh interval={4000} /> without whenHidden. RiderAlert raises a system notification only when a poll brings in a new job id. With the tab hidden there are no polls, so the alert built for the "phone in pocket" case can't fire in that case. The vendor board already fixed this for the kitchen (line 846).

P0 Pushes are fire-and-forget on a serverless runtime

Every notify*() is called as void notify…(), e.g. vendor-orders.ts:472,490,529, cancel/route.ts:123-124, rider-dispatch.ts:472,477. On Vercel, work that is still running after the response is sent may be frozen or dropped. The code already knows this: dispatch is awaited "because an un-awaited write is one a serverless runtime may abandon". Observability uses after() for the same reason (lib/obs/emit.ts:163). The pushes don't, so some may never leave the server.

P1 Admin / Manager moves skip dispatch and the rider

  • overrideOrderStatus (admin/orders/actions.ts:131-134) and manager advanceOrder push the customer, but never call dispatchOrder. An order an operator moves to kitchen or ready gets no rider offer.
  • assignRider (manager/actions.ts:105) writes the assignment but sends the rider nothing.
  • No cancel path pushes the rider. cancelDeliveryForOrder only updates the row.
  • Admin cancel doesn't reach the vendor as a push (vendor has no push id, see first finding).

P1 Offer expiry is passive

EXCLUSIVE_OFFER_MS = 180 000 is checked only when someone reads the board (offerStateFor). When a rider ignores an offer, nothing re-dispatches to rider #2 and nobody is pushed. The order silently becomes "open" and waits for a rider who happens to look. Admin only flags it at 8 min (admin-dispatch.ts:32).

P1 Dispatch "nearest rider" uses stale positions

reportDriverLocation writes only onto an assigned/picked_up delivery. An idle rider reports nothing, so "nearest" means "where their last delivery ended, up to 30 min ago". A rider on their first job of the day has no position and sorts last.

P1 Confirm migration 0042 is live

The 25 Sept bug-fix pass found 0042_rider_dispatch unapplied in production. Without it writeOffer returns "unsupported", so there is no exclusive offer and no upcoming-pickup list. Dispatch is reduced to "fastest thumb at ready". Re-check before relying on the tree above.

P2 Smaller gaps

  • One device per user. profiles.onesignal_id is a single column. A vendor with a counter tablet and an owner phone only gets pushes on whichever registered last.
  • English-only push text. onesignal.ts:52-53 sends { en } only. For a Hindi-first Bemetara audience, add hi (OneSignal picks by device language).
  • No push to admin/manager for the "unassigned 8 min" or "vendor hasn't accepted in 3 min" alarms.
  • Stale doc comments: order-events.ts:73 says the vendor board polls every 4 s (it's 8 s). build-plan.ts:468 says the same.
  • Admin dashboard (/admin) has no auto-refresh, so its numbers are fixed at page load.

5 · Cost of polling (rough estimate)

Every tick is one Vercel function run plus every Supabase query on that page. Assuming a modest day of 20 vendor tablets and 3 ops screens open 12 h, 10 riders on shift 10 h (screen on about half the time) and 200 orders tracked for about 35 min each:

SourceIntervalRequests / day
Vendor boards (poll even when hidden)8 s~108 000
Customer tracking (visible ~40%)3 s~56 000
Rider boards (visible ~50%)4 s~45 000
Admin orders + manager4 s~32 000
Rider GPS writes10 s~24 000
Total≈ 265 000 / day · ≈ 8 M / month

More than 95% of these ticks find nothing new. The cost grows with open screens, not with orders.

6 · Suggestions, in order

Step 1: close the "screen off" gap (small changes, biggest win)

5Apply migration 0042 (and 0039/0048/0051) to productionSupabaseXS
6Fix the stale comments (kitchen-alert, order-events, build-plan)XS

Step 2: make dispatch self-driving

  • Offer sweeper. A Vercel Cron (every minute) or pg_cron job finds unassigned deliveries whose offer is older than 3 min. It re-runs dispatchOrder excluding the rider who ignored it, and pushes the next rider. After 2 misses it pushes the manager.
  • On-duty location. Add an "On duty" toggle for riders. While on duty with no job, report position every 60 s to a small rider_presence table. Dispatch then uses real positions and can skip off-duty riders.
  • Ops alarms by push to admin/manager: vendor hasn't accepted in 3 min, no rider in 8 min.
  • Multi-device push: call OneSignal.login(user.id) and target by external_id instead of one stored player id. Every device a person signs in on then gets the push.
  • Hindi push copy alongside English.

Step 3: replace polling with Supabase Realtime (the real fix for speed and cost)

Use a "signal, then refetch" pattern. A database trigger on orders and deliveries sends a tiny message ("order X changed") on a private Realtime broadcast channel: restaurant:{id}, rider:{id}, order:{id}, ops. Each screen that receives one calls the router.refresh() / tracking fetch it already has. This keeps all data reads going through the existing, RLS-checked server code. It also avoids postgres_changes, which would stream whole rows (customer phone, address) to whoever subscribes.

  • Keep AutoRefresh as a 30 s safety net, and on reconnect.
  • Rider GPS can go on the order:{id} channel directly. The customer map gets a fresh point within about 1 s of the fix instead of 6–13 s, with no DB write per tick needed for display.
  • Realtime only helps while a page is open. Push (Step 1) is still what wakes a phone in a pocket. The two work together.

Suggestions from the live test, in order

  1. Apply migration 0042 in production. This turns on the rider's "coming up" offers, the 3-minute hold and the sweeper's re-offers.
  2. Mark COD as paid when the rider confirms delivery with cash, so admin, settlements and the cash ledger agree with the rider.
  3. Show the rider on the vendor card ("Ramesh · picked up 2 min ago"), and move picked-up orders out of "Ready".
  4. Close out stuck orders. Cancel #D8A8DA3D and #5AF16BC6 and add an auto-close for orders stuck more than 24 h, so customers never see "27 days late".
  5. Fix dark-console contrast on the vendor and admin headers and alert banners. Remove the duplicate "Live" badge.
  6. Hindi across the customer, vendor and manager apps, starting with order status, checkout and the vendor board. The rider app's "English / हिंदी" pattern already works.
  7. Bigger tap targets and a 12 px text floor on phone screens. Header icons to 44 px.
  8. Checkout: auto-pick the nearest deliverable saved address, and say "outside delivery area" before the button is pressed.
  9. Rider GPS heartbeat: also send a position every 20–30 s even without movement while a delivery is active.
  10. Speed up the heaviest polls: /admin/orders (2.8 s every 4 s) and /admin (6.4 s). Then move the boards to Realtime (Step 3), which removes most of this load.
  11. Verify push on the production domain with a vendor tablet and a rider phone that have armed alerts.
